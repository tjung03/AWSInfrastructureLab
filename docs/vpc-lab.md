# VPC 구성 관계와 재실습 점검

[저장소 소개](../README.md)

모듈 03의 상세 노트와 모듈 04의 VPC 인프라 실습 목록을 바탕으로, 공개·비공개 경로의 차이를 설명합니다. 아래 주소는 노트의 **사설 CIDR 설계 예**이며 실제 계정의 VPC ID나 접속 주소가 아닙니다.

| 위치 | CIDR | 라우팅 및 대상 |
|---|---|---|
| VPC | `10.3.0.0/16` | 공개·비공개 서브넷의 주소 공간 |
| 공개 서브넷 | `10.3.0.0/24` | 로컬 VPC 경로, `0.0.0.0/0 → 인터넷 게이트웨이`; 공개 EC2와 당시 실습의 공개 NAT 게이트웨이 |
| 비공개 서브넷 | `10.3.1.0/24` | 로컬 VPC 경로, `0.0.0.0/0 → NAT 게이트웨이`; 공인 IPv4가 없는 EC2 |

노트에는 공개 서브넷과 비공개 서브넷을 **서로 다른 가용 영역**에 배치한 첫 구성이 적혀 있습니다. 이후 두 번째 공개·비공개 서브넷을 추가하는 단계가 있지만, 처음에는 NAT가 하나입니다. 이 단계에서 NAT가 위치한 가용 영역에 문제가 생기면 다른 영역의 비공개 서브넷도 해당 NAT를 통한 외부 연결을 잃을 수 있습니다. 후속 고가용성 모듈에는 두 번째 NAT 추가 항목이 별도로 기록되어 있으나, 이 저장소는 해당 구성을 재현하거나 검증하지 않았습니다.

## 작업 순서와 확인할 항목

| 순서 | 노트의 작업 | 재실습 시 확인할 항목 |
|---|---|---|
| 1 | 사용자 정의 VPC와 공개·비공개 서브넷 생성 | CIDR이 서로 겹치지 않는지, 각 서브넷의 가용 영역이 의도대로인지 |
| 2 | 인터넷 게이트웨이를 VPC에 연결하고 공개 라우팅 테이블에 경로 추가 | 공개 서브넷과 해당 테이블의 연결, 기본 IPv4 경로의 대상 |
| 3 | 공개 EC2에 웹 서버를 준비하고 네트워크 설정 확인 | 공인 IPv4 유무, 필요한 포트에 한정된 보안 그룹, 인스턴스와 로컬 웹 응답 |
| 4 | 공개 NAT 게이트웨이를 공개 서브넷에 두고 비공개 라우팅 테이블에 연결 | NAT의 상태, 탄력적 IP, 비공개 서브넷의 기본 경로 |
| 5 | 공인 IPv4 없는 비공개 EC2를 시작 | 인스턴스 주소와 보안 그룹, 허가된 관리 경로, 외부로의 연결 여부 |
| 6 | 테스트 후 리소스 정리 | EC2 종료, NAT 삭제와 탄력적 IP 해제, 라우팅·게이트웨이·VPC의 종속성 |

공개 서브넷이라는 이름이나 기본 경로 하나만으로 외부 접속이 보장되는 것은 아닙니다. EC2의 공인 IPv4, 보안 그룹, 네트워크 ACL과 OS 방화벽도 확인해야 합니다. NAT 경유 외부 통신 역시 경로·NAT 상태·보안 규칙과 실제 대상 서비스의 응답을 구분해 살펴야 합니다. 보안 그룹은 필요한 프로토콜과 접속 출처에 맞춰 제한하고, 노트의 암호 기반 SSH 설정을 재사용하지 않습니다.

이 표는 당시 환경의 테스트 성공을 의미하지 않습니다. 노트에 남은 `ping`, `curl`, 라우팅 확인 명령은 *수행할 검사 항목*으로만 취급했습니다. 실제 검증 결과를 남기려면 날짜, 리전, 익명화한 구성, 요청과 응답, 정리 결과를 별도로 기록해야 합니다. 비용이 발생할 수 있는 NAT·탄력적 IP·EC2 등은 계정의 현재 요금과 할당 상태를 확인한 뒤 생성해야 합니다.
